## Обязательные исправления содержания

### 1. Неверная буква ответа про pgAudit

- Вопрос: `sql-foundations-m15-exam-q19`.
- `modules/module-15/module_exam.md`, строки 225–233: правильный ответ про аудит и журналирование — **B**. Под **C** написано «Для шифрования столбцов».
- `modules/module-15/answer_key.md`, строка 592: указано **C**, хотя приведён текст варианта B.
- В том же ключе объяснение неправильного B тоже не соответствует реальному варианту B.

Исправить букву на B, переписать разбор оставшихся A/C/D. Иначе ученик с правильным ответом будет получать ошибку. Назначение расширения подтверждается [репозиторием pgAudit](https://github.com/pgaudit/pgaudit).

### 2. Скрипт проверки схемы падает на ORDER BY

- Файл: `modules/module-08/examples/shopdb_ddl_verify.sql`, строка 20.
- Исходная строка: `ORDER BY table_name::text, constraint_name;`.
- PostgreSQL: `ERROR: column "table_name" does not exist`.

`table_name` здесь — псевдоним выходного столбца. Его нельзя таким образом использовать внутри выражения приведения типа в ORDER BY. Например, заменить на `ORDER BY conrelid::regclass::text, conname;` либо вынести проекцию в подзапрос и сортировать снаружи. Проверить весь скрипт повторно: исходный прогон с ON_ERROR_STOP останавливается на этой строке и не проверяет оставшиеся запросы.

### 3. Разрешённая вставка в RLS-примере не работает

- Файл: `modules/module-15/examples/row_level_security_lab.sql`, строки 8, 13–16 и 40–41.
- Таблица получает IDENTITY с начальным значением 1, затем строки 1, 2, 3 вставляются с явными ID.
- Объявленная как разрешённая операция `INSERT ... (tenant_id, amount) VALUES (101, 700.00)` получает сгенерированный ID 1 и падает с `duplicate key value violates unique constraint "tenant_orders_pkey"`.

Это проверено от имени `shopdb_runtime` с установленным `shopdb.tenant_id=101`, то есть проблема не в RLS. Явная вставка ID не продвигает identity sequence. Нужно согласовать её следующее значение с seed, например задать START WITH 4 либо корректно вызвать setval после seed. Затем отдельно проверить разрешённую вставку, запрещённую вставку и изменение tenant_id. После ожидаемой ошибки в транзакции требуется ROLLBACK/отдельная транзакция или SAVEPOINT; простое продолжение после ошибки некорректно.

### 4. Неверный запрет REFRESH CONCURRENTLY внутри транзакции

- `modules/module-13/03_materialized_views.md`, строка 68.
- То же правило повторяется в README, авторском интерактиве ex05, ученических условиях и практических материалах модуля 13.
- Утверждается, что `REFRESH MATERIALIZED VIEW CONCURRENTLY` нельзя выполнить в transaction block.

Проверено обратное на установленном PostgreSQL 18.6: BEGIN → изменение исходной таблицы → REFRESH MATERIALIZED VIEW CONCURRENTLY → чтение обновлённого значения 150 → ROLLBACK успешно выполнились. Это не `CREATE INDEX CONCURRENTLY`, у которого другое ограничение.

Сохранить действительные требования: заполненное materialized view, подходящий UNIQUE-индекс по столбцам без WHERE и выражений, несовместимость с WITH NO DATA; убрать ложный запрет транзакции. См. [официальное описание команды](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html).

## Совместимость с AnswerBook

### Повторные интерактивы в одном уроке

В восьми модулях нарушено правило «не больше одного интерактива в уроке»: 1, 4, 10, 11, 13, 14, 15, 16. В частности, модули 1, 13 и 16 имеют только 3/4/4 урока: разместить в них минимум пять интерактивов по одному на урок математически невозможно.

Нельзя исправлять это созданием пустых уроков. Нужно согласовать содержательное перераспределение/объединение небольших модулей либо изменение правила. В модулях с достаточным числом уроков можно перенести упражнение в другой подходящий урок или оставить пять лучших. В рамках аудита структура не менялась.

### Название формата не доказывает реализуемость упражнения

Текущий data-transform допускает фильтрацию, проекцию существующих полей, сортировку, дополнительную сортировку, группировку и подсчёт. Не допускает SQL JOIN, SUM/AVG, оконные функции, вычисляемые поля, разворачивание одной записи в несколько, NULL в исходной схеме или состояние SQL-транзакции.

Примеры несовместимых спецификаций:

- `m04-ex04`: COUNT с NULL, SUM и AVG — требует другой механики/подготовленной трассы.
- `m05-ex02`, `m05-ex05`: результаты JOIN, а не цепочка поддерживаемых преобразований.
- `m09-ex03`: развернуть повторяющиеся столбцы в строки и добавить line_no.
- `m10-ex05`: вычислить новое поле order_size через CASE, затем сгруппировать.
- `m11-ex05`: оконная скользящая SUM.
- `m12-ex07`: состояние UPDATE; `m13-ex06`: жизненный цикл TEMP TABLE.
- `m16-ex04`: JOIN, вычисляемая сумма и оконный итог.

Их учебный смысл подходит курсу. Следует перенести их в code-trace, code-order, matching или другой реально подходящий формат либо отдельно расширять движок. Полноценную SQL-семантику нельзя обещать одной заменой названия формата.

Часть code-debug также требует пересмотра. Например, `m11-ex03` предлагает вместо ошибочного WHERE вставить целое CTE-решение. В движке выбирается одна ошибочная строка и готовая замена; нужно сконструировать корректное окружение и варианты, а не требовать произвольного редактирования всего запроса.

В поздних спецификациях часто есть только смысловой эталон («принимать эквивалентное SQL-решение»), но нет конкретных блоков, вариантов, ID узлов, всех состояний или перечня принимаемых ответов. Это редакторские заготовки; детерминированную проверку ещё требуется спроектировать при переносе. Code-assembly нормализуется в code-order, а не добавляется как восьмой тип.

## Методические замечания

- В 33 уроках модулей 2–6 обе «промежуточные» проверки стоят после всех основных объяснений и примеров, непосредственно перед итоговым тестом. Их следует распределить внутри урока.
- В модуле 2 насчитано 168 одинаковых объяснений дистракторов «этот вариант не выполняет требование вопроса; правильное правило приведено выше». Они не объясняют конкретную ошибку ученика. Заменить содержательным разбором каждого неверного варианта.
- У многих ранних вопросов заведомо нелепые дистракторы: например, обычному SELECT противопоставляются удаление строк или создание таблицы. Для первых проверок допустимо, но итоговые тесты стоит усилить правдоподобными ошибками, небольшими таблицами и точными результатами.
- В `m02-ex08` объяснение утверждает, что проекция не содержит price, хотя эталонная проекция — `product_name, price`. Там же нужно отличать учебный порядок стадий от семантически эквивалентных цепочек; фильтр и сортировка в этом примере допускают перестановку без изменения результата.
- В десяти ключах текст не дословно совпадает с выбранным вариантом. Девять случаев выглядят как сокращение/перефразирование или опечатка, а не доказанная ошибка правильного ответа; один случай с pgAudit — реальное противоречие буквы и смысла. Не заменять все ключи автоматически.
- Manifest не фиксирует версию PostgreSQL, хотя материалы используют PostgreSQL-специфичные возможности и ссылки на версию 18. Лучше зафиксировать целевую основную версию и отдельно реальные версии проверки.
